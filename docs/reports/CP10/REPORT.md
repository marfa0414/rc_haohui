## 冻结验收条件

- 可复现 Compose：单 all 和 API + 两个 Worker；独立迁移与运行账号、具名 PG 卷、健康检查、有界停机和真实 Worker 强杀恢复。
- 基线：10 租户、约 1 KiB、20 rps 持续 600 秒，供应商 200/100 ms；接入 P95 ≤ 300 ms，数据库 acceptedAt 至首次实际业务 HTTP 开始 P95 ≤ 3 秒（含 Token 等待），另报首次预留延迟。预热单列，12000 个计划请求及所有受理任务完整对账。
- 压力：固定阶梯输入、有效 429/503、资源曲线、拒绝与受理分开统计、恢复排空。
- 突发：A/B 各 100 个任务，A 前 15 秒超时后恢复，B 始终 200/100 ms；B 全部 10 秒内成功、全部 A 至 60 秒成功，验证在途上限、重试时间和 200 个受理任务。
- 指标：已知操作计数增量、任务状态与 PG 一致、未来调度排除在最老可执行等待之外；真实 Hikari 等待可观察。

## 开发期诊断与修复

迁移和权限定向测试 3/3 通过（15:02:03）。指标首次定向测试 6/8 通过：测试夹具触碰不可变快照、单连接池不能同时满足 Flyway 迁移锁与迁移连接。修复为只调整可变调度时间、使用两个真实连接并占满后测试第三个等待者。第二次 7/8 通过，发现 Hikari PoolStats 短时缓存导致释放后立即读 Gauge 仍是旧值；改为有界等待实际 Gauge 更新后再通过 ADMIN HTTP 断言归零，没有删断言或放宽数据库约束。第三次于 15:12:49 完成，8/8 通过。以上定向结果不代替累计门禁。

官方镜像服务多次网络超时。通过公开镜像缓存取得官方索引指向的 ARM64 镜像，逐项校验索引、平台 manifest 和 config SHA-256，实际运行 `java -version` 及 `curl --version` 成功。构建以任务专用本地标签引用同一镜像，避免 BuildKit 再次请求超时的 metadata；Dockerfile 的默认官方摘要保留。摘要链见 [base-images.json](base-images.json)。

Docker 启动曾长时间停在 created、PID=0。移除宿主 bind 后仍出现等待，无挂载探针同样延迟，随后恢复，根因未确认，不能宣称已经证明是文件共享故障。最终部署将初始化脚本及应用部署配置 COPY 入镜像，以减少运行时宿主依赖；所有业务模板仍存数据库，环境变量继续覆盖预算与凭据。没有删除数据卷或重启 Docker Desktop。

首次累计门禁于 15:13:16–15:19:39 执行 `clean verify`，51 个套件、531 项全部通过，失败/错误/跳过均为 0。期间 Java、测试、构建依赖输入未变；仅 Dockerfile、.dockerignore、compose.yaml、deploy/README.md 四个部署文件调整，分别保留调整前及最终哈希，最终部署另以实际镜像构建与启动验证。没有用重复不受影响的 Java 测试替代容器实测。

基线原始采集使用本机 Python 3.9.6。分析首次遇到 PostgreSQL 五位小数秒时，旧版 `datetime.fromisoformat` 报错；使用 Python 3.12.14 对同一未改动的原始数据分析后通过，独立审计也采用 3.12.14。工具文档最终最低版本改为 3.11，以支持 PostgreSQL 可变小数位的 ISO 时间戳。该环境问题不改变时间戳或分位算法。

`burst-001` 明确失败：计划 200 条，192 条实际受理，8 条由于发流器 128 并发槽位已满而记为 `INJECTOR_CAPACITY`，没有发送给 API；192 条受理记录均最终成功。不能据此签 200 条门禁。修复仅将正式突发阶段的发流器上限设为有界 200，保持其他阶段 128、固定 100 ms 输入窗口和原来的 10 s/60 s 目标，使用新 run-id 重跑并保留失败原始证据。

## 结论与边界

固定基线、过载拒绝、突发隔离及真实强杀恢复均达到本阶段条件。所有限流、熔断、Token 缓存与执行池仍属于进程；增加 Worker 会叠加本地额度。单机 Compose 与单 PostgreSQL 不提供数据库高可用证明；生产容量、跨机网络、TLS 握手成本和供应商实际限额需要在目标环境重新验证。CP11 仍需完成全新目录／数据卷演示、交付文档和最终用例追踪。
