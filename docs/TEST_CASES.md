## 1 测试范围与通过标准

覆盖 PRD 的 FR01–FR12、AT01–AT28、NFR01–NFR07，以及安全、并发、配置变更和资源有界性。Redis、MQ、集群级严格限流、单 Token 全局协调、数据库介质损坏恢复、任意脚本和供应商业务码解析均不作为 MVP 已实现能力验收。

所有纳入冻结范围的用例最终均须通过。P0/P1/P2 表示失败修复优先级，不表示 P2 可以不执行。参数化用例的每个列明变体都必须执行并保留结果。禁止通过 `skip`、`disabled`、删除断言、放宽业务契约或仅重跑幸运样本掩盖失败；环境缺失应记录为阻塞／未执行，不能显示为通过。需要改变范围或指标时，先更新评审记录，不得倒推修改要求以配合结果。

类型缩写：U 为纯逻辑单元测试；I 为真实 PostgreSQL 集成测试；E 为 HTTP 端到端测试；F 为独立进程／网络故障测试；S 为安全测试；P 为性能或资源测试；R 为人工审阅。一个用例可有多个层次，不能用 U 替代其要求的 I/E/F 证据。

以下表格是冻结的用例目录，不把执行实例数当作用例覆盖数。已执行子场景见 [CP01](reports/CP01/REPORT.md)、[CP02](reports/CP02/REPORT.md)、[CP03](reports/CP03/REPORT.md)、[CP04](reports/CP04/REPORT.md)、[CP05](reports/CP05/REPORT.md)；跨阶段用例必须补齐剩余证据才能最终标为 PASS。每个用例给出前置条件、操作和可判定断言；公共夹具见第 2 节。CP 编号与后端开发检查点一致。

95 项中，90 项计划仅依赖自动化证据，5 项同时需要人工审阅；其中 8 项涉及性能／资源验证，16 项涉及独立进程或网络故障。类型可交叉，后两项数量不与前两项相加。审阅项不是替代自动化的豁免。

## 2 环境、数据和可控测试设施

### 2.1 环境约束

- 数据库使用与开发部署一致大版本的真实 PostgreSQL，并执行正式迁移；不使用 H2 替代唯一约束、JSONB、`SKIP LOCKED` 或事务行为。
- 普通集成测试可以使用容器数据库，进程崩溃、双 Worker 和端到端测试使用独立 JVM/容器，保留数据库持久卷。每个测试使用独立数据库/schema或独立租户、事件命名空间，清理只针对测试环境。
- Mock 供应商包含业务端点、OAuth Token 端点和独立控制面。生产出站校验默认启用；仅隔离的开发／测试配置显式允许指定 Mock，不允许全局关闭 SSRF 或 TLS 校验来使安全测试通过。
- 单 Worker 测试验证进程内缓存、熔断和冷却；双 Worker 测试验证租约及状态正确性。不能对两进程声称「全局只取一次 Token」「全局只放行一次探测」。
- 记录应用构建 SHA、Java/PostgreSQL 版本、操作系统、CPU、内存、数据库位置、实例数、连接池与并发参数、测试时间和配置摘要。

### 2.4 时间、随机数和进程注入

纯逻辑测试使用可注入时钟和可复现随机源，验证退避范围、安全窗口与截止边界。SQL 租约和调度必须使用数据库时间；集成测试通过测试专用短时配置、屏障或受控设置测试任务到期时间推进场景，不能只修改 JVM 时钟就假定数据库时间也改变。

故障配置必须满足 `Token 超时 < attempt 总上限 < 租约`，并为慢 CI 留出观测余量。例如快速故障测试可使用 1 秒 Token 超时、2 秒业务超时、4 秒 attempt、12 秒租约；具体数值在 CP01 校准并记录，不改变生产默认规则。基线压测使用记录在报告中的正常配置，不套用极短测试参数。

需要以下仅测试可用的屏障：`afterTaskCommitBeforeResponse`、`afterClaimBeforeReserve`、`afterReserveBeforeSend`、`afterProviderResponseBeforeWriteback`、`beforeConditionalWriteback`。注入逻辑必须默认关闭，生产构建／配置无法被请求参数开启。进程崩溃测试在屏障到达后终止独立 Worker，并验证另一个 Worker 或重启进程恢复。

等待使用带明确截止时间的状态轮询或事件屏障，禁止无限等待。失效场景必须有负断言窗口，例如「冷却到期前 Mock 业务请求数不增加」，不能只检查最终成功。

### 2.5 并发、隔离和突发场景的固定参数

下列为测试覆盖参数，不修改生产默认 10 个全局槽位／每供应商 3 个槽位。报告中必须记录覆盖值。

| 场景 | 固定输入与配置 | 明确判据 |
| --- | --- | --- |
| Token 50 等待者（AUTH-03/11） | U 层使用独立 `TokenProvider` 的 50 个并发调用线程与屏障；E 层若要求50个同时执行attempt，显式将全局和该供应商槽位覆盖为50，HTTP/DB资源配置保持有界 | 不把默认10/3下排队的50个任务称为50个同时等待Token的线程；健康获取一次；失败等待有界，冷却窗内不逐个击穿 |
| 供应商隔离（GUARD-05） | 单Worker，全局10、每组3、扫描100ms、业务超时2s；一次提交A组30条和B组10条，停止继续输入；A持续超时，B固定100ms返回200；观察20s | A在途≤3、总在途≤10；B首次HTTP开始均在5s内、10条B在10s内成功；进程待执行队列不超过显式配置上限；PG积压不要求自动为0，初始40条可按预算进入终态 |
| 突发和恢复（OPS-05） | 单Worker，全局10、每组3；一次提交A/B各100条后停止输入；A前15s持续超时后切200/100ms，B始终200/100ms；扫描100ms、业务超时2s、退避基数100ms/上限1s、熔断冷却1s、最多12attempt、总期限120s；观察至60s | B全部在10s内成功；A恢复后到60s全部成功；全局/供应商在途不超10/3，进程队列和连接不超配置上限；实际发送不早于nextAttemptAt，所有已202任务可对账；报告积压峰值和排空时间 |

有限突发场景通过固定输入测量排空；持续输入高于吞吐的情况仅由 OPS-04 验证接入保护，不能要求 PostgreSQL 积压在没有拒绝策略时天然有界。MVP 未承诺集群级 QPS 或专门的平滑放量算法，恢复场景以并发上限、既定重试计划和资源界限检验是否出现失控发送，不把「无重试风暴」作为无定义断言。

## 6 执行与报告契约

当前 `./mvnw clean verify` 已实际运行并覆盖截至当前阶段的累计测试，报告位于 `docs/reports/CPxx/`。下列其余 make 命令仍为计划接口，不能当成已有脚本；最终 README、CI 与报告须使用实际可运行的命令，依赖缺失或断言失败必须返回非零。

```sh
./mvnw verify
make test-integration
make test-e2e
make test-fault
make test-security
make test-load-baseline
make test-pressure
make verify-all
```

- `verify` 应运行本地逻辑与约定的集成测试，若容器运行时不可用则明确失败／阻塞，不自动跳过PG测试。
- `test-fault` 应自动启动独立进程，执行命名屏障、终止和恢复，输出AT12～AT16等窗口证据，不把人工模拟替代成一组mock函数调用。
- `test-load-baseline` 必须按固定到达率产生流量，记录计划到达率、实际到达率、HTTP结果、超时、丢弃的负载迭代和排空结果。生成器容量不足导致低于20rps不能算达标。
- `verify-all` 汇总测试清单，逐项检查95个用例与参数变体是否有执行证据，性能与人工审阅不因独立命令而遗忘。所有报告绑定同一候选提交和环境参数。

报告建议写入运行专用目录，例如 `reports/{runId}/`（待实现），至少包含：

| 工件 | 必须记录 |
| --- | --- |
| 用例结果表 | caseId、参数变体、CP、提交SHA、状态、开始/结束时间、失败原因、证据路径 |
| 自动化结果 | JUnit XML或等价结构化结果，包含失败、错误、跳过数 |
| 故障证据 | 屏障到达、终止PID/实例、数据库任务和attempt快照、Mock请求/副作用计数及时间线 |
| 性能结果 | 环境、配置、样本数、实际输入速率、接入与投递P50/P95/P99、状态对账、资源峰值和瓶颈 |
| 安全结果 | 允许/禁止目标连接计数、TLS断言、敏感标记扫描；不得输出真实Secret |
| 人工审阅清单 | README可复现性、部署限制、AI使用说明真实性及审阅人/日期 |

建议最终汇总状态限定为 `PASS / FAIL / BLOCKED / NOT_RUN`；未执行不得默认为成功。性能目标未达时标记失败并列出差距，不把“已有报告”当“指标通过”。若经用户明确接受调整目标，先修订PRD与验收基线再重新测试。

| 宕机后结果 | 预留后、发送前屏障知道未发，但真实系统不一定有可靠证据 | 已预留但未完成记录按UNKNOWN恢复，不以测试屏障知识伪造生产事实；仅明确认证失败才NOT_SENT |
| 重投幂等作用域 | replayRequestId作用域与同键不同参数未完全规定 | 唯一键采用任务ID+replayRequestId；同键同参数复用原操作结果；同键不同原因/expectedRun冲突；优先查幂等再判当前状态 |
| 首次投递延迟 | 性能目标中的“首次开始投递”需要时间点 | P95≤3s按数据库acceptedAt至首次业务HTTP开始发送计算，包含Token等待；另报acceptedAt至首次attempt预留的调度延迟，不用后者替换前者；所有已受理但未发送任务单列失败/未完成，不能剔除 |
| 2xx超大Body | PRD要求HTTP确认和限制读取，但没有规定读取截断如何分类 | 在有效响应头已确认且不需要Body判断时可丢弃并关闭/安全释放连接；不为读全Body无限等待；应由HTTP客户端策略冻结 |
| Token畸形响应 | 未完整定义缺expires_in、非法JSON、3xx等终止细类 | 确定性协议/配置错误终止并脱敏；网络/429/5xx重试；任何路径都不得无界获取；由CP06固定错误码 |
| 表单空值 | 只接受“非空标量” | 空字符串也拒绝，0/false合法；若要允许空字符串应修改明确约定后同步MAP-05 |
| 缓存授权参数 | Scope顺序是否影响缓存没有列出 | 只有协议上等价的集合先规范化排序去重；配置版本变化仍产生独立上下文，不能跨租户合并 |
| 熔断忽略样本 | PRD只统计指定业务错误 | 普通4xx/408/429/认证错误均不计成功或失败；有效2xx计成功；不能把排除错误算成功稀释失败率 |
| 负载目标 | PRD为拟定、待实测目标，用户要求最终用例全绿 | 初始20rps/10min和P95目标作为本轮基线；未达标是待修复/评审项，不因“目标建议”而伪标通过 |

## 8 非自动化审阅与不保证事项

人工审阅仅用于判断说明的真实性、取舍的清晰程度和从全新环境按文档操作的可复现性。功能正确性、故障恢复、Token竞态和安全限制不能用“人工读代码认为没问题”替代测试。

README和AI使用说明必须明确：有限重试不保证任意故障下最终成功；2xx不等于业务副作用；供应商不幂等会重复；本地Token缓存、冷却和熔断不提供集群全局约束；数据库容灾与业务端Outbox不在当前保证范围。供应商不允许多个Token共存时，现有多Worker认证方案不适用，不能用Mock成功代替真实接入判断。

AI使用说明的审阅依据是实际历史对话与后续真实变更，不能虚构“用户否决了某建议”或“已运行全部测试”。当前按已批准的 checkpoint 顺序实现并验证，阶段报告仅说明对应范围，完整交付须补齐全部用例及参数变体。
